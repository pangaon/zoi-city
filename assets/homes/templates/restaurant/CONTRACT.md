# Generic restaurant Concierge

`renderRestaurantHome(entity,publishedDesign=null)` in `api/_restaurant-home.js` returns a full HTML document only when `verticalFor(entity).v.key==='restaurant'`, UUID is valid and explicit visibility is not hidden/unpublished. Other types, including bakery, return null for their own adapters. Caller keeps entity lookup/404/cache/publication authorization and JSON-LD. Default layout is Concierge; other generic restaurant layouts are not yet implemented. Specialized Avli four-layout selection can keep precedence.

Uses existing `profileOf`, `profileForVertical` and `profileMedia`: owner overrides/clears retain precedence, website enrichment provides fallback, interface artwork is filtered by shared media helper. No Avli address, phone, timezone, menu, photos, service offering or call-hour defaults exist. `restaurantData(entity,profile,media)` exports a pure browser-safe content model. Description/contact/menu/hours/socials/catering come only from recorded fields. No open-now claim or venue coordinate is inferred; directions require a street address. An explicit international phone from profile may supply the dial link only if its digits match the existing local phone suffix; no country code is guessed.

`renderRestaurant(content,design)` accepts shared section order/hidden fields and copy headline/intro/offerings_title/gallery_title/calendar_title/contact_title. Menu text and prices remain escaped source text, no currency or available inventory invented. Menu URL opens an in-Zoi source panel with attributed optional embedded preview and explicit original-source fallback. Important tested limitation: the real Tasty Greek HTML menu refuses/does not render in an iframe; default no longer displays a giant blank frame. This is NOT claimed as full in-app menu ingestion. Structured existing menu records render completely within Zoi. Safe source-menu extraction into structured records remains necessary for parity where a provider blocks embedding.

Actual customer tools:
- Per-restaurant published menu/contact/social/source links and gallery with keyboard navigation.
- Personal visit planner: actual restaurant identity/contact; chosen date/party/questions; no seating/capacity assumption. Valid date/party1..50 only. Browser-local persistence namespaced by listing UUID, readback verification, copy/edit/clear and storage failure states. Explicitly no message, reservation, order or payment.
- On explicit click, anonymous `booking_catalog(p_listing,p_from,p_to)` checks actual next7day capability. Only `{ok:true,available:true}` reveals `/book/?listing=UUID`; no slot count or availability claim until that real booking screen.
- Separate `inquiry_availability` check reveals `/inquiries/?listing=UUID` only for enabled actual owner inbox. Error supports retry, never silently treated as unavailable or success.
- Existing external reservation/order provider handoffs are explicitly labelled. Actual purchases remain with provider.
- Owner workspace entry uses existing `/social/`; shared owner design publication is handled by root's authorized editor, not this module.

No live booking/enquiry mutation or real messages. Durable scripts `.recovery/scripts/restaurant-{browser,capability}-check.cjs`; outputs `.recovery/logs/restaurant-browser-results.json` and screenshots.
