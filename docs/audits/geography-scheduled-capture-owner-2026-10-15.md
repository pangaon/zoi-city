# Trusted main scheduled source capture candidate

The actual public GitHub repository is `pangaon/zoi-city`, default branch main, neither archived nor disabled. The included repository metadata report records those fields without credentials. The new workflow uses only the standard `ubuntu-latest` runner, no cache/artifact/custom-image step, and no new service or purchase. GitHub's current [Actions billing documentation](https://docs.github.com/en/billing/concepts/product-billing/github-actions) says standard hosted runners in public repositories are free. This does not claim arbitrary future private/larger-runner/storage usage is free.

The workflow runs on trusted main every five minutes, offset from the hour, or through an explicit new manual dispatch. It refuses rerun attempts and untrusted repository/ref/event contexts. A second runtime metadata check refuses a private/renamed/default-branch-changed/archived/disabled repository before the Vault token is read. GitHub concurrency plus the existing database singleflight bounds overlap. [GitHub's schedule documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) specifies default-branch execution, a five-minute minimum, possible delays/dropped runs during load and automatic public-schedule disabling after 60 inactive days. This is not a punctual execution guarantee.

The narrow script uses the existing trusted CI `SUPABASE_ACCESS_TOKEN`, and the existing automatic read-only GitHub token. It reads exactly the existing `geography_repair_source_token` Vault value through the Management API with a read-only fixed query. Secrets stay in memory and are masked before use. It neither provisions/rotates tokens nor extracts service keys. It invokes the deployed source consumer once with `{}` and allows no redirects, retries, deploys, queue writes, schedule SQL, providers or coordinate changes. Output contains validated bounded counters or fixed diagnostic labels. HTTP uncertainty is not rerun within that invocation. Twelve mocked transport/redaction/guard tests pass.

A successful scheduled invocation is still a release gate, owned by the lead. This candidate has not been committed, enabled or invoked live by the specialist. Existing hosted worker archive-budget, source limits, capture lease and canonical job handling stay in force. This is source research/private evidence capture, not proof that public client profiles or addresses were corrected. A zero eligible batch is not the end of the catalogue.

The separate private queue investigation found a PUBLIC table SELECT privilege on the extension-owned queue, but an actual anonymous `Accept-Profile: net` request selecting only id with limit0 returned406/PGRST106: the running API exposes `public, graphql_public`, not net. No queued rows/headers were read. The connected postgres role lacks the platform owner's grant authority. Thus role ACL alone does not demonstrate external Data API exposure; legitimate platform-owner hardening remains a separate optional action. The provisional guarded queue migration was not applied. The existing bootstrap's stricter private-queue cron guard is unchanged, and future bootstrap requests must use `install_schedule=false` while this alternative is being accepted.

Release: independently review the new script/workflow and safe-log tests, merge to trusted main through the lead, observe one actual successful scheduled event and persisted bounded job results, and retain existing DB singleflight. Do not call the new schedule full enrichment or equate cron submission with completed profile updates.
