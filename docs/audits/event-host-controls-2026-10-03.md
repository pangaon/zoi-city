# Reusable event organiser controls — isolated candidate

This candidate connects a current authorised event owner’s dated sales update to guest pages and brings the existing booking/payment controls into one event-scoped entry. It is not deployed. No database, production inventory, account or provider mutation was performed by this lane.

## Scope and source contract

Base: `95d63fd15b18d3d73d91bb2a5e40ae54313e8a39` in the isolated checkout `/workspaces/zoi-city/.recovery/event-host-controls-20261003`. The active community-release runtime was not edited. Runtime changes are exactly `assets/events/host-controls.mjs`, `host-controls.css`, `assets/events/signature/customer-a.mjs`, `customer-a.css`, `experience.mjs`, and `tickets/hosts/index.html`. No room/model/source-plan furniture, source pricing, poster, venue date or publication state changes.

Toronto’s generic URL redirects to its static page, so its source record was read through the actual anonymous `home_entity` RPC; Montréal/Kalamata used their current canonical public model. These source fetches do not establish operational ownership or verified sales. All displayed 317 counts and configured stock/prices in tests are controlled owner fixtures, never published live facts.

The defect was precise: generic/Montréal and promoter renderers already read reviewed owner publicity, but the ordinary static Toronto guest page never read it. Its HTML also lacks a sales slot. The shared customer setter now creates a single inline slot before the hero’s fine print, and the existing event lookup passes `publicPublicity` only after current event type/slug/identity checks. Exact current event URL matching, owner clears, expiry/future time, and machine-only exclusion remain the existing shared policy. Sales imagery and room screens are untouched.

The new control desk mounts only with one valid workspace and event parameter. It requires successful current `bizpage_status` identity and `home_content_get` permission/receipt before showing fields. The existing writer `home_content_save` receives only `p_base:{}` plus `p_profile.event_publicity`; source biography, date, artists, URLs, pricing, base values and other owner fields cannot accidentally enter this patch. It uses the existing publicity editor, validator and guest renderer. Untouched fields are omitted; explicit removal sends null. Save snapshots use current CAS plus an immutable request reference; unknown results lock edits and retain the exact public announcement request for same-request confirmation after reload. Account/scope changes retire the view and separate pending requests. Refused auth/CAS clears the editable snapshot.

The backend contract remains unchanged: `home_content_authorize` permits current owner/admin/editor for the authorised listing. Inventory and payment writers require the current owner/admin and matching event workspace. The UI does not promote an editor to an operator. Booking setup opens `mountOrganizerSetup` from the existing allocation surface; allowed payment arrangements focus the existing `mountEventPaymentPolicy`. Existing table setup enables/disables real configured timed holds. Existing payment policy offers none or unpaid pay at the door plus a response deadline; online remains false/unconnected. No automatic inventory or pricing is inferred from a plan, tier colour, source count or announcement.

Supabase RPCs invoke existing database functions; [official function guidance](https://supabase.com/docs/guides/database/functions) was checked. The current changelog was fetched; no Supabase SDK/schema change is part of this packet.
