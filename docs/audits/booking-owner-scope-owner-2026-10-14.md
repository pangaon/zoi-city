# Booking owner account and workspace safety

The existing booking operator captured its workspace and used authenticated RPCs, but lacked a surface lifecycle/account fence and a final-dispatch scope check. A workspace switch during token refresh could dispatch the original workspace write. A delayed read could repopulate private customer data after an account switch.

The shared operator now uses the existing private operator lifecycle and clears its private surface/data on account change, workspace change or disposal. Every canonical booking RPC checks scope before the call, through Core's synchronous `beforeDispatch` hook after its final token wait, and after the response. Current access refusals remove editable private controls. The suite returns the teardown handle and protects an in-flight mutation from ordinary tool disposal. Booking writer parameters, version checks, reschedule request identities, planner nonces and stores are unchanged.

Source: `assets/bookings/operator.mjs` and `assets/suite/bookings.js`. Applicable to all workspaces using the existing booking suite, including configured staff/table/performer/venue/equipment booking resources. This is an owner-tool correction, not proof of every family's public home or actual stock/availability.

Rendered and exercised: actual operator in Chromium at 390 and 1440 pixels, with controlled canonical RPC responses. Twelve cases cover sign-out customer-data clearing, same-account workspace switch during held token refresh with zero write dispatch, delayed private-read discard, in-flight original save response after account switch with no false success or resend, current role refusal, and normal original-owner save. No overflow or page errors. Fifteen existing booking model/planner/reschedule/pending checks pass. The delayed Core token callback is controlled by the browser fixture; existing Core implementation supplies the production beforeDispatch hook.

Production capability remains pending independent review and the release lead's source deployment/readback. No live booking writes, provider calls, email, payments or stock changes were performed. An already dispatched canonical mutation may finish after the actor changes; the new surface never labels that original-account response as the new account's save. Existing create-item/slot writer ambiguity and full unsaved form recovery are separate follow-up requirements; this change does not add a receipt store or claim those operations fully reconciled. Reschedule and planner scoped nonce recovery retain their existing contracts. Online deposits and external calendar sync remain explicitly unconnected.
