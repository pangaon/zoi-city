# Unified owner publication: implementation proposal and release gates

Status: read-only code audit and proposed contract, not implemented or production accepted.
Baseline: origin/main 839b398; current release worktree. User-facing date: 2026-10-13 (Toronto).
Ownership: owner/home specialist prepared this artifact. Integration/release lead owns migrations and coordinated rollout. No shared schema or public writer was changed by this audit.

## Current capability and evidence

`assets/suite/bizpage.js` reads an authenticated, versioned `home_content_get` snapshot, keeps proven owner social removals authoritative, and submits basics/profile together to `home_content_save`. The database writer serializes authorization and listing access, compares a content fingerprint, persists a request receipt, and returns the original receipt for the identical authorized retry. The current-session migration strengthens `zoi.home_content_authorize` before locks and after lock waits. This is an immediate public content write, not a private content revision.

`assets/homes/editor.mjs` and the home-design tables provide private design saves, authenticated inert HTML preview, publish, and historical design restore into a draft. Preview-before-publish is currently a client check (`previewed` equality); the publish RPC itself has no server preview receipt. `api/home-preview.js` takes a design and renders against currently stored content. It cannot preview unsaved menus, descriptions or media together as one revision.

`home_media_save` immediately updates `listings.profile.owner_media`, with its own version and receipt ledger. Empty owner media is authoritative. Its authority helper is separate from the newer current-session content helper: equivalent fresh-session/role/ownership checks after lock waits must be demonstrated before reuse, not assumed from code similarity.

Native basic editing uses `mobile/src/businessOwner.ts` and versioned content snapshots; full structured menu/media/design editing hands off to the web editor with separate browser authentication. `mobile/src/MusicEditor.tsx` still calls the legacy profile writer directly. A web-only change to the new editor cannot establish native parity or prevent older native writers from publishing outside the new flow.

Evidence in this specialist run: 20/20 unit tests passed for profile persistence, owner snapshot identity/authorization, and four-design render parity across creator, event, music, professional, health and restaurant families; JavaScript syntax passed. One bounded local candidate change makes an unconfirmed `pendingContent` save count as unsaved for navigation protection. No new source retrieval, browser screenshots, database execution, production edit/public readback, or physical-device test was performed. No all-family completion claim follows from these tests.

## Smallest coherent design

Extend the existing `zoi.home_designs`, history and request ledger rather than create a second editor/content authority. Keep `draft`/`published` design columns and existing public design response compatible. Add nullable versioned `draft_content` and `published_content` envelopes plus their immutable publication history snapshots. Existing rows stay in legacy mode until explicitly activated by a compatible owner editor. One common revision counter covers design and staged content/media updates; one CAS fingerprint covers the public baseline used by that revision.

The envelope is schema-versioned and includes only whitelisted owner-managed content: base field patch, vertical profile field patch, optional media collection and the captured baseline content/media version. Design remains the existing validated full design object. Omission means leave untouched; explicit null/empty strings, empty arrays and empty dictionaries mean clear. Never serialize `_enrich`, leases, credentials, guardian data, private workspace metadata or operational inventory into this envelope or public projection. Store the exact owner field-presence map with history so restoration cannot resurrect imported fallback. URLs/media use existing server validators and canonicalization; no raw embeds.

Draft patches remain separate from canonical published listing fields until publish. Preview merges draft patches into the current authenticated snapshot, including `owner_content` provenance and proposed `owner_media`, then runs the same family renderer as public output. Published listings remain the canonical public content source; no parallel public profile store or copied per-client sites. Operational booking/festival/property records remain in their existing tools and are referenced by stable IDs; this proposal does not privately stage inventory, prices in a connected provider, or booking outcomes.

Extract and reuse the existing content/media validation and canonical application logic as private helpers; do not nest public RPCs with synthetic request IDs. A single publication transaction reauthorizes the current session and role, locks actor/membership/listing/revision in one documented order, rejects transferred ownership or stale public fingerprints, validates current operational IDs, applies content/media and published design, records complete revision history and the exact receipt, then commits. Failure at any point leaves all public fields unchanged. Existing helpers must preserve unrelated profile keys and enrichment provenance.

Existing published content should be snapshotted on activation without marking imported values as owner edits. Historical restore creates a new private candidate against the current baseline; it never publishes immediately. Removed operational IDs are filtered/flagged, unavailable assets are flagged, and transferred-owner private histories remain inaccessible to the new workspace. Source/enrichment changes invalidate preview and require review or an explicit field-aware rebase; never silently overwrite proposed owner values.

## Shared web/native contract

Proposed authenticated RPCs (names are a design proposal, not advertised APIs):

- `home_revision_get(workspace, listing)` returns validated identity, mode/schema capabilities, revision, public baseline fingerprint, draft design/content/media, published revision and private history summaries.
- `home_revision_change(workspace, listing, request, expected_revision, action, patch)` supports save and restore. It returns an exact workspace/listing/request/action/revision receipt; identical authorized retries return the same receipt, changed request payloads fail.
- Private preview endpoint accepts saved revision and baseline fingerprint, fetches the authorized proposed snapshot, and renders it inertly. It returns HTML plus a server-minted preview ID bound to account, workspace, listing, revision, baseline and renderer version. HTML itself is never trusted as proof. Draft/baseline changes invalidate that preview.
- `home_revision_publish(workspace, listing, request, expected_revision, expected_baseline, preview_id)` requires a matching unexpired server preview receipt and current authority. Editor can save private drafts; owner/admin publishes by default. Existing teams currently allow editors to publish designs: expose this role change explicitly in capability response and verify existing expectations before activation.

Both clients distinguish local edits, private saved draft, previewed revision, publishing, confirmed publication, conflict, refused access and uncertain outcome. Each durable request is account/workspace/listing scoped; uncertain results lock new edits and retry the identical request only after reauthorization. Persistence, if required, stores only the minimal encrypted native/private browser request according to established storage controls, clears rendered data on account change, and never automatically replays. Navigation offers recovery rather than silently discarding pending writes.

Web page details, media and design panels become views of this same revision controller. Saving updates the private draft; one explicit publish action updates all three. Native basic editing uses the same revision APIs. Full structured editing can retain a clearly labeled authenticated browser handoff initially, with no tokens in URLs and explicit reload after return. Native direct profile/music writes and legacy web/API writers must recognize staged mode and refuse with `home_revision_required` (or route through a compatible draft operation); otherwise they bypass approval. Never turn an old 'Save publicly' request silently into a private save while returning its old success receipt.

4. Implement web controller and native shared contract before staged activation. Update copy to state actual save/publish semantics. Browser tests at 390px/desktop cover populated restaurant menu edits, sparse professional/creator record, empty media/social removal, keyboard/focus, reload, lost response, account/workspace change, conflict/rebase and historical restore. Exercise the exact dialogs and result states.
5. Run isolated database and preview API integration with test records, then edit -> private save -> preview -> publish -> public API -> rendered desktop/mobile readback. Record source identity, projected values, rendered evidence and exercised journey separately. Confirm no draft leakage in public entities/search/cache/SEO and all family renderer routes. Preview rejection for unsupported families must stay explicit; it is not publication acceptance.
6. Device tests verify iOS/Android native edit, separate-browser sign-in/handoff, app backgrounding, stale session, publication reload and private draft recovery. Record supported native controls versus deliberate web handoff; do not label a responsive screenshot as device parity.
7. Independently review candidate, migration rollback and application rollback. Roll back staged activation safely: do not allow an old client to bypass newly promised private approval. Deploy reviewed migration and compatible clients together, activate isolated acceptance workspaces first, verify actual production version/public readback, then expand. Lead owns deployment and evidence. Provider operations are outside this publication transaction and require their own confirmed outcomes.

## Remaining product scope

This proposal covers publication of owner home content, media links and visual design. It does not deliver provider media ingestion/transcoding, social distribution, full team approval delegation, arbitrary external website deployment, inventory edits or native structured-edit parity. Those remain separate requested capabilities with explicit ownership. No action from George is required to complete the code design; actual provider accounts/fees, if introduced later, need precise owner setup requirements and authorization before spending.

## Implemented candidate and final specialist verification

The proposal above preceded implementation. The candidate now extends the existing design tables and canonical writers through `20261014040454_home_unified_owner_revision.sql`, uses `assets/homes/design-editor-revision.mjs`/`.css` in Business home, and previews through `api/home-revision-preview.js`. Schema rollout still defaults every home to legacy mode; only an owner/admin's explicit activation enables staged writes. Before activation the controller requires an authenticated schema-1 revision snapshot, the new preview endpoint's exact schema/renderer readiness, and a successful supported canonical renderer preflight. A failed staged revision getter does not fall back to the legacy editor.

The no-new-secret implementation records an authenticated actor/revision/baseline-bound preview workflow receipt. An authorized caller can invoke the confirmation RPC; this is intentionally not proof of independent visual review. Publication remains guarded by owner/admin authority, current-session helper, exact CAS baseline and preview expiry. Independent rendered acceptance stays a separate release requirement.

Preserved legacy content/media/design requests can return their already-successful exact receipt after activation, following current authorization and unchanged-payload checks. New staged legacy writes and boolean profile writers are refused. Public wrappers retain existing named-role execute grants, keep PUBLIC/anon revoked, and recheck current authority after the preserved writer returns, so a delayed legacy operation cannot return a successful result after a newly refused session. Private originals are not directly callable by authenticated clients.

Restoration captures the complete canonical managed base fields and the actual presence of whitelisted profile/media keys. Missing historical profile keys are removed on restoration, while null/empty historical fields remain explicit clears. Internal removal flags are server-owned and excluded from client save payloads. A separate staged baseline hashes render identity, family, geography and visibility as well as the unchanged legacy content hash. Family/name/identity changes invalidate previews until explicit rebase.
