# Native owner website and source-review parity — producer candidate

The prior native BusinessEditor used legacy `bizpage_get` and a boolean `bizpage_save` response. It had no version conflict guard, exact lost-response replay or saved source-review panel. This candidate replaces the contact-details flow with the existing `home_content_get`/`home_content_save` contract, while retaining the full editor handoff and separate music editor. It creates no new suite or provider feature.

All work is isolated in `.recovery/native-owner-source-candidate`. The current release checkout and prior freezes remain unchanged. Five runtime files are owned: BusinessEditor.tsx, businessOwner.ts, businessOwnerRecovery.ts, BusinessSourceReview.tsx and the narrow assets/suite watchFolder addition to metro.config.js. The accepted Company resolver and watchFolders stay intact. The exact accepted source-health state model, ownerEntity, official-source policy and Company modules are explicit dependencies, not edited copies of those modules.

Native owners see the published website separately from their draft, source identity holds and the imported source hostname. They can focus the address, restore the saved public choice, choose a new official URL or explicitly remove the link. Invalid schemes/userinfo are refused. Reviewing a source does not claim to refresh or verify it. All source-review behavior uses the shared web model.

Only changed base fields are sent, with an empty profile patch; menus, imported provenance, profile explicit nulls, media namespaces and untouched fields remain in the existing writer's authority. Current account/workspace is checked before and after token waits and responses. Authorized private snapshots and verified current ownership status surround every save attempt. Role refusal clears private editor values. Returning to the app rechecks access/version and blocks stale drafts until reviewed.

Unknown results preserve the exact request/version/payload in memory, lock further editing and offer the same-request retry. Durable recovery stores only account-scoped workspace/listing/request/version references, never contact text, websites or tokens. The existing backend has no receipt lookup/cancel RPC. After remount the owner therefore reauthorizes, reviews fresh saved details and explicitly clears the interrupted reference before editing again. A fresh read is never presented as an exact old-request receipt. If saved records changed during review, the newest values must be reviewed again.

Source evidence: read-only current installed definitions and actual function SHA/ACLs are retained in installed-contract/auth/writers/dependencies JSON. Anonymous Café Boulis source data is retained from the accepted source-identity packet. No actual customer's authenticated editor contents were fetched or changed. Browser owner rows use an explicitly synthetic private fixture around those source fields.

Rendered evidence: actual compiled Expo App at 390 touch and 1440 desktop; inspected owner-choice/source-panel and sparse validation screenshots. Buttons wrap on phone, labels/inputs remain readable and no horizontal overflow occurs. Saved choice and source attribution are clearly distinct. The fixture never alters application styling or motion to manufacture screenshots.

Exercised evidence: 13 focused units, full native 439, TypeScript, all three web/iOS/Android Expo exports and 28 compiled journeys pass. Browser journeys cover choice→draft review→publish→clear→reopen, malformed/lost receipts with exact immutable replay, conflict and reviewed saved records, nonce-only remount, viewer denial, delayed read and delayed save replies across account/workspace switches, refusal before dispatch, and sparse unsafe URL rejection and actual AppState foreground callbacks with changed version or revoked access. Legacy writers are never used by the new contact-details workflow. Source maps prove exact new editor/client/recovery/panel plus shared state/owner/policy modules in all three platform exports.

Actual isolated PG runs 11 groups with retained installed SQL SHA/ACL reproduction, anonymous/private receipt access refusals, website-only real writer→same receipt→reopen→explicit clear→real public_owner_content→reopen, byte-identical imported menu/profile/null preservation, ownership/role denial and two concurrent CAS writers with one winner. Session-expired private reads and ownership status are denied.

One inherited backend gap remains proved: an expired session can replay an old `home_content_save` receipt before downstream current-session checking. Native's fresh guarded reads block this path, but this candidate does not modify schema or claim to harden all backend callers. A schema correction is separate work. Existing MusicEditor still has its separate legacy profile writer; this bounded website/contact parity does not silently claim that music editing has migrated.

Initial browser fixture failures (timing before an authorized draft existed, missing synthetic seo_entity response for the inherited MusicEditor, ambiguous multiple alert selector) and initial TS inferred-JS-options failure are retained separately. Runtime changes only address the approved owner workflow; no old assertions were removed. React review checked hook cleanup, keyed scope clearing, current authority guards, direct imports, safe storage schema and accessible controls.

Not deployed. Physical iOS/Android devices, store distribution, actual authorized live customer edit→public readback and backend session correction remain open. Commands are in tests/browser/native-owner-source/README.md.
