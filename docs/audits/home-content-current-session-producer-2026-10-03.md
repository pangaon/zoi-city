# Shared owner content authorization candidate

The actual installed owner save can return an old successful receipt after its Auth session expires or is removed. The isolated fixture reproduces that defect using retained installed definitions before installing the candidate. This candidate changes only `zoi.home_content_authorize(uuid,uuid)`, shared by the versioned owner read/save and legacy base/profile writers. It is a proposed backend correction; no production schema or customer records were changed.

Supabase CLI generated `20261003052809_home_content_current_session.sql`; the generation receipt is retained. Exact current-definition, ACL, owner, search path, volatility and definer preflight guards cover 22 captured dependencies and callers. The helper replacement retains its private postgres-only ACL, signature, SECURITY DEFINER status and empty search path. All 21 other captured definitions remain byte-identical. There are no grants, new helpers, RLS changes or writer payload changes.

The helper reuses the installed volatile `zoi.workspace_invitation_email(false)` current verified account/session guard. It checks before any caller can reach the prior-receipt path, then after every existing profile, membership, listing and conditional approved-claim lock. Passing `false` adds no Auth row locks, preserving the existing profile → membership → listing → claim order. The profile lock result additionally must still match the current Auth account; remapping the actor while it waited cannot authorize the old actor. The existing qualified membership, owner-listing and approved-claim checks retain their meaning and refresh after waited row updates.

The reused guard requires a UUID session belonging to the current Auth account, current session `not_after`, verified nonempty email, no deleted or anonymous account and no current ban. It uses `clock_timestamp()` and fresh volatile statements. JWT signature/expiration remains the existing API boundary responsibility; this SQL candidate does not implement token verification or extend the underlying Auth policy. The accepted native candidate performs fresh authorized reads before and after publication, but that client behavior alone was not counted as backend receipt authority acceptance.
