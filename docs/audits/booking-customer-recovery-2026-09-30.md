# Booking customer audit and recovery

Candidate files: `assets/bookings/customer.mjs`, new `assets/bookings/pending.mjs`, `tests/unit/booking-pending.test.mjs`, `supabase/migrations/20260930083803_booking_create_public_moderation_guard.sql`, `tests/database/booking-moderation.integration.mjs`, `ops/qa-booking-moderation-rollback.sql`.

Live definitions inspected read-only on 2026-09-30. Availability already requires an enabled schedule, current owning workspace, published clean/cleared listing, active services/resources, future slots and no existing active reservation. Booking creation locks the customer/profile and resource, verifies reviewed slot version, enforces party capacity and one active booking per slot, and replays the same customer's request ID. Its direct-call listing guard omitted moderation; the narrow migration inserts only that predicate into the actual function definition, fails if the expected fragment is not unique, and preserves the rest of the deployed function and grants.

Web recovery now saves account/listing/request/slot/quantity/version before sending. No name or email is persisted in that state. Unknown outcomes keep the same nonce through availability refresh and page reload. In the same page, retry uses the frozen original payload. After reload, Check booking status matches the request against the current user's real booking history; a missing match remains unresolved and prevents another booking. It does not fabricate failure or automatically issue a fresh request. Known transactional rejection codes release the latch so updated availability can be reviewed. A confirmed receipt is checked against request, slot, quantity and supported current status; a subsequent refresh failure does not erase confirmation.

Account changes clear rendered history and contact inputs. Late previous-account history responses are rejected. The public availability page can remain open while the private form is hidden. Provider reservations/payments are never implied by this workflow; prices are due at venue and no payment is collected here.

Hotels and car rentals: the existing hotel family exposes source-provided rooms, amenities and an external provider availability link when present. There is no multi-night room inventory/channel-manager integration or car-fleet/date-range rental contract in this appointment/resource module. The shared booking schedule requires owners to configure services, resources, availability and enable settings. A source booking URL is not proof of configured Zoi inventory. No new hotel/car capability is claimed.

Verification: 21 real PostgreSQL checks including concurrency, capacity, moderation and the exact dedicated-QA rollback fixture; three request-persistence unit tests. Local browser fixture exercised simulated commit-then-lost-response, reload retaining nonce with zero extra writes, history recovery, account-signout DOM clearing, and delayed prior-account history rejection. 390/1440 viewport widths matched document width. Screenshots and reproducible fake-RPC fixture are private `.recovery/logs/booking-recovery-*`; no production booking was made. The current user's history is bounded to 100 rows: a very old unresolved request outside that list remains blocked and requires contacting the business, rather than being treated as absent.

Release should bump the `book/index.html` customer module cache version when batching these assets. Browser fixture evidence is not live authenticated acceptance or hotel/car provider integration evidence.

Follow-up review fixed the guest→OTP transition: only a successful explicit OTP verification restores the previously selected public slot/nonce after account synchronization. A swap between signed-in accounts never preserves private draft state. Core now emits a payload-free `zoi:auth-change` event after session save/clear, including refresh; booking listens for immediate same-tab cleanup. RPC cleanup runs in finally so Core's own stale-session rejection cannot bypass it. Twelve Core/pending unit checks pass. A browser fixture using the actual Core implementation with strictly intercepted fake OTP/RPC responses completed choose-before-sign-in→OTP→one confirmation call; same-tab auth.clear synchronously removed private history/contact, and delayed rejected old-account work did not restore them. No real OTP was sent. Additional files: `assets/zoi-core.js`, `tests/unit/core-auth-events.test.mjs`.
