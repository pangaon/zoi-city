# Company Operations and private-document session authority proposal

Unapplied next-batch candidate. The current company console frontend is a separate accepted release. This proposal makes no customer-data mutation, provider claim or government formation/filing claim. Production access in this lane consisted solely of read-only function, policy and table metadata. Exact retained definitions, ACLs, source-consumer inventory, RLS policies and table ACL/RLS state are in the evidence directory.

## Scope and dependency boundary

The Supabase CLI2.115.0 generated `supabase/migrations/20261003032635_company_document_current_session.sql` using `supabase migration new company_document_current_session`. The generation receipt is retained. The deterministic proposal builder derives replacements from actual installed definitions, preserving SQL argument/default/return shapes, minimal receipt hashes and IDs, cancellation locks, existing payload validation, parent scopes, expected-version checks, upload reservations, object keys, history/version and download semantics.

The installed `zoi.ops_role(uuid)` serves36 function consumers and two direct-read policies. Twelve relevant authenticated Company/Operations/document RPC definitions change here;24 consumer definitions remain unchanged. Settings, audience, AI, creator, appearance, timekeeping, festival, football and property are not accepted as session-hardened by this patch. The broad role helper itself remains byte-identical. The internal receipt projection also remains unchanged behind the now-fenced RPC wrappers.

The candidate adds a private `zoi.company_document_authority` helper and an authenticated boolean RLS session predicate. The authority helper is callable only by PostgreSQL-owned functions; it validates the existing installed `suite_current_session` contract at entry. Before each RPC return, it locks the current Auth user/session and profile/workspace membership, checks the same actor and the required current capability, then checks current session time again after the last membership/profile lock. This last check prevents natural `not_after` expiry during that final lock wait. Any refusal aborts the function transaction, including tentative record/audit/receipt or upload writes.

Required capability follows the existing suite: workspace members may read Operations; owner/admin/editor may write contact/project/task and read private documents; owner/admin manage company/archive/cleanup. Saved company receipts retain their existing management gate. Current role labels are refreshed after reader waits, so a downgraded reader does not receive the old owner label. Task assignment is checked and locked again before a saved result; explicit null assignment and deadline clears remain valid. Every original return path is fenced, including replay, missing and cancellation results.

Only the exact existing Operations record/audit SELECT policies gain a current-session predicate. They retain their prior workspace-membership condition. Private document and receipt tables retain their existing private ACLs/RLS. New helpers carry empty search paths and PostgreSQL ownership; anonymous and service clients cannot invoke the authority helper, and only authenticated readers receive the boolean RLS predicate.

The service-only `document_upload_finish` and `document_cleanup_finish` definitions and ACLs remain byte-identical. Trusted worker completion does not require a caller JWT, and revoking a client session is not represented as cancellation of an already reserved trusted worker job. The existing uploader-membership check after the document lock is exercised independently, as is client inability to finalize bytes. This patch introduces no upload-session binding and does not claim new physical-storage/provider acceptance or broader worker hardening.
