# Dedicated authenticated QA read journey

Manual main-only workflow `.github/workflows/authenticated-qa.yml`, pinned repository pangaon/zoi-city. No workflow invocation is authorized by this file; parent release review must happen first.

The runner reads exactly the approved existing Auth user, checks its pinned UUID and QA email marker, then uses Supabase admin.generateLink magiclink and verifyOtp token_hash. GenerateLink does not send mail. It does not create/reset a user or change a password. The returned session must match the same user; zoi_me must return the pinned profile and owner membership of the dedicated QA workspace. A mismatch fails before business reads.

Service credentials remain in the Node process and are never passed to the browser. The agent-browser0.38.1 process receives no inherited Supabase/token/secret variables. The short-lived user session is transferred through an in-memory local CDP socket, never shell arguments, files, URL parameters, screenshots or artifacts. A document-start storage adapter keeps authentication storage in JS memory; browser persistence and service workers are not used. All browser requests are intercepted: only public static assets and an exact allowlist of read RPCs are allowed; workspace/listing parameters are bound to the preflight QA scope. Sends, saves, bookings, payments, email OTP and arbitrary API calls are blocked.

Checks: actual Core signed-in state; actual private zoi_me identity and workspace; mounted Business home form or legitimate claim-first state; optional home_content_get only if bizpage_status returned an owned QA listing;390/1440 horizontal bounds. No owned listing is explicitly reported as not exercised, never a successful owner-edit journey. These checks do not cover saving, preview publication, conflict recovery or device-native flows.

Finally the browser closes and `/auth/v1/logout?scope=local` revokes only the newly issued session's refresh capability. Supabase access JWTs can remain usable until their expiry; this is not an immediate JWT invalidation claim. Runner cancellation or infrastructure termination can interrupt cleanup, so the workflow has no persistent credential artifact and its session is not reused. On success the only uploaded file contains fixed booleans, viewport numbers, commit/time and an explicit scope statement. No private names, emails, content, request bodies, response bodies or network logs are exported. Failures emit a fixed generic message and no artifact.

Five mocked tests cover exact identity guards, generate/verify/local-logout sequence, wrong identity before generation, cleanup on workspace/browser failure, absent owned listing, and browser write/cross-scope denials. Production execution is pending parent review; no authenticated production acceptance is claimed yet.

Official references: [generateLink](https://supabase.com/docs/reference/javascript/auth-admin-generatelink), [verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp), [signOut](https://supabase.com/docs/reference/javascript/auth-signout), and [Auth client REST implementation](https://github.com/supabase/auth-js/blob/master/src/GoTrueAdminApi.ts). Changelog checked September30; current PostgreSQL upgrade notes do not change this Auth sequence.

The current GitHub integration cannot dispatch workflows through the Actions API (403). A deliberate change to the expiring QA request file can instead trigger the same ordinary main-branch CI job. The script requires attempt 1, exact repository/main, exact request identity and a 30-minute expiry, exact push ancestry, dedicated identity and pinned code hashes; unrelated pushes do not run it. This does not grant any new credentials or business write capability.

A reviewed push request is now also supported because this integration cannot dispatch Actions manually. The request is bound to the exact preceding commit, the changed request file, pinned QA identity and SHA256 of all three auth-QA modules. The checkout fetches two commits. Forced/deleted/created push events, mismatched repository/ref/head, unchanged requests, rerun attempts, altered code and expired requests fail before credentials. The maximum issue-to-expiry window is30minutes; validation runs both before browser installation and immediately before loading credentials. This is an event-bound first attempt, not a database-backed global exactly-once guarantee. No production run is claimed merely from preparing the request.
