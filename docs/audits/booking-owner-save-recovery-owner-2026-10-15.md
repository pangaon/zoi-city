# Booking owner exact save recovery candidate

A committed create with a lost response could be repeated with no ID and create another service/resource. An update's version conflict could not recover the original successful receipt. A confirmed save followed by a failed refresh could also leave a create form pointing at no record.

The new authenticated `booking_owner_save` wraps the existing canonical settings/item/slot writers in one transaction with an immutable request receipt. The receipt binds request, auth account, canonical profile, workspace, kind, exact payload and captured client. Original signatures, canonical records, business constraints, locks and expected-version checks remain in use. This journal stores mutation evidence, not another resource or booking catalogue. Replays authorize current owner/admin/session and current configured/captured listing ownership before returning the old result; they grant no new mutation authority. A current client transfer blocks new writes and recovery without changing the stored receipt. Private edits to still-owned unpublished pages remain possible; the existing public catalogue visibility gates remain unchanged.

The existing booking operator selects the new API only after an authenticated schema1 capability receipt for its account/workspace. The browser persists an exact original request before dispatch. Unknown replies retain that marker and disable changes; Retry sends the same nonce and original payload. Account/workspace changes clear the private surface. The original actor can reopen and recover its receipt. A confirmed result retains the canonical identity/version immediately; a failed refresh cannot convert the next edit into another create. Current permission failures remove the editable surface. The suite asset version is updated coherently.

Source evidence: migration `20261014165715_booking_owner_save_receipts.sql`, `assets/bookings/owner-save.mjs`, existing operator/suite hook and scoped regression fixtures. The migration refuses deployment without the reviewed current venue authority helper (body MD5 `8f8f063b04975a1673c48dff85851f1a`, postgres owner/private ACL).

They include all four save kinds, immutable replay after later edits, actor/profile/account/workspace conflicts, current-client transfer, own unpublished-page visibility, role/session refusal, strict payloads, business validation rollback, real concurrent duplicate creates/updates and concurrent listing transfer. No always-allow/deny authority helper is substituted.

Setup, service, resource and availability saves recover lost replies; service create recovers after reopen; updates increment once; pending account switch shows no false Saved; original-account return recovers the same object. A confirmed save plus failed refresh preserves canonical identity for the next update. No overflow or page errors. Local identity/RPC transport and response loss are controlled; these are not production customer transactions.

Validation: 24 booking model/helper/planner/reschedule/pending unit checks and 12 prior account/workspace lifecycle browser checks pass. The production rollback/no-public-operation fixture is prepared separately for the release lead; it has not been executed by this specialist. No live database mutation, provider request, public booking, customer contact or deployment was performed.

Release requires independent SQL/browser review, reviewed schema application, production rollback fixture/readback and coherent source deployment. Historical legacy requests have no new receipt retroactively. Compatibility editing when schema1 is absent uses the old API and does not acquire exact nonce recovery; an existing pending new request is never routed to that legacy path. Production acceptance therefore requires schema1 to be verified. Preserve receipts/pending markers during recovery; use a forward source correction, not deleting receipts or replaying a request through an old writer.

This is a web owner-tool improvement shared by configured booking families. It adds no native editor; iOS/Android owner booking UI/handoff acceptance remains open. It does not establish lodging stock, customer booking authority outside these owner endpoints, online payments, calendar sync, source-complete public homes or every organizer operation.
