## Session setup and write boundaries

Allow 10 minutes for setup, 35 minutes for assigned journeys and 15 minutes for recording/retesting failures. Assign one primary tester to each row below; pair another tester with any serious defect before concluding it is fixed.

Use a clean browser profile where practical. Test phone width around 390px and desktop around 1440px; actual phone Safari/Chrome is more valuable than a second desktop screenshot. Sign in only with the tester's assigned account. Never share the internal CI QA account or paste tokens into a report. An owner/editor test requires explicit assignment to the private QA workspace and an appropriate role; a normal new account has no right to edit existing customer businesses. Do not claim a restaurant, publish a synthetic event, make a real reservation, vote artificial artist demand, send greetings/email, connect a personal social account, pay, or post test noise publicly merely to get a green result. Where no isolated operational fixture is assigned, test the entry/gating and mark the transaction **blocked by missing test fixture**.

The private owner CI fixture is labelled **ZOI INTERNAL QA — NOT PUBLIC**. It is not a customer business or a normal creation/claim test. Its cleanup preserves an archived, hidden tombstone and immutable receipts; it may remain visible to the dedicated QA workspace. Do not publish, delete or reuse it independently.

## Evidence labels

- **Production read exercised:** actual public/authenticated read or navigation was observed; writes and the whole journey are not thereby proven.
- **Fixture exercised:** real UI/model code ran against explicitly mocked responses, or local/rollback-only database tests. Production/device execution is still needed.
- **Device pending:** compiled/exported or built, not yet exercised on the stated device.
- **Blocked:** required fixture, owner role, provider configuration, signing or integration is absent. Honest empty/disabled UI is the expected outcome.
- **Candidate:** implemented locally but needs an explicit release receipt before testers can expect it live.

## Report format and stop conditions

One report per defect: tester number; UTC time; exact URL or native build ID; account role (never password/token); device/OS/browser; precise steps; expected/actual result; screenshot with contact data redacted; reproducibility; whether a write might have reached the server. Include the exact public listing identity when reporting wrong source content.

Stop the affected journey and contact the coordinator for cross-account private data, wrong-person identity/contact, unexpected public publication, duplicate reservations/charges, or an ambiguous mutation result. Preserve its request/reference in the application; do not clear storage, create a new request, or repeatedly tap submit. Report honest unavailable/empty states separately from broken loading, missing actions or misleading promises.

End-of-session outcome for each row is **passed in named environment**, **failed with evidence**, **blocked by named prerequisite**, or **not run**. A screenshot or HTTP 200 alone cannot close a transactional test. Release coordinator collects the 20 outcomes and assigns remaining defects; no aggregate “all ready” label while these boundaries remain.
