# Community publisher authority and source review

Read-only review of actual production function definitions on2026-10-14, plus current `supabase/functions/social-publish/index.ts`. No provider requests, feed insertions or publication calls were performed.

## Observed gaps

`zoi.publish_social_to_community` locks the post first. Its authenticated path checks workspace membership and original author identity, without the canonical owner/admin/editor/current-session guard. Its worker path does not check the current original author role, original client ownership or source evidence freshness before inserting a public feed row. The receipt replay branch can update a post before these checks. Linked UPDATE triggers currently protect human writes; auth-null service publication only receives the editorial date/revision check after the feed insert. This cannot establish safe automated delivery after team/client revocation.

The actual `public.social_due_posts()` projects only `id,workspace_id,body,media,channels`. The Edge worker expects `post.meta` for body overrides, threads and first comments, but does not receive it. Existing submit/approve/reject RPCs call current workspace authority, then change status; no approver identity or approved content snapshot is recorded in those functions. A scheduled status alone does not prove that a current approver approved the currently edited body.

## Smallest coherent next change

1. Keep existing canonical posts, private AI/editorial links, approval statuses and delivery receipts. For the bounded current-authority fix, validate the existing canonical author against current workspace permission and user state, and derive original client context from private links. Do not infer an approver identity from scheduled status or silently substitute a different actor. A revoked original author requires explicit owner recovery; preserve the post and refuse new delivery. Exact approved-content identity remains a separate approval-workflow gap, to be solved in the existing canonical workflow if that capability is claimed.
2. Acquire workspace first, then current actor/profile/member/user authority, optional original client/source authority, and finally the canonical post. Discover its workspace using an unlocked read, then recheck after locking. Reuse the foundation's owner fallback and forged-owner handling. A service job does not need a live browser session, but its canonical author must still be an eligible current writer and active user; a human call requires the actual current session as well. Coordinate the exact shared order with canonical writers and client helpers before changing SQL.
3. Before a NEW public feed insert, validate canonical author authority, due status/time, selected Community destination, current original client ownership, and any linked editorial source's active exact revision/snapshot/date/jurisdiction and evidence freshness. Existing successful immutable delivery receipts may be recovered without a second side effect; recovery must not create a new publication after authority is lost.
4. Return the exact saved metadata in the service-only due snapshot, but perform final authorization inside the atomic Community delivery function. Snapshot filtering alone is not authorization. Keep unsupported thread/first-comment checks and use the actual saved body override.
5. External providers need the same check before their network request and a durable target attempt bound to the exact canonical delivery payload. Do not promise cross-service atomicity: a database guard after the provider call is too late. Preserve uncertain provider outcomes and prevent blind replay; provider-specific receipts and reconciliation are a separate gate.
