# Reuse substantive source HTML in the existing enrichment evidence flow

Read-only implementation proposal. No further source requests, retry, code edit, lease or database mutation was made for this plan.

## Confirmed missing link

The production Edge worker already uses the right first decision: `supabase/functions/zoi-enrich/index.ts` fetches a guarded document, calls `_document-quality.js::inspectSourceDocument`, refuses challenges, routes JS shells to repair, checks member-source scope, and passes substantive HTML to the existing `extract` function. It may fetch at most two explicit same-origin supplementary pages through existing guards. This is not a missing extraction algorithm.

`scripts/enrichment/extractor.mjs::extractRenderedSource` compiles and reuses that same deployed `extract` body and shared image/social/media/menu helpers; despite its name it accepts plain source HTML. `_images.js::extractSiteImages` already handles source meta, srcset, lazy data-src and inline background candidates and classifies auxiliary/rating/logo/menu imagery. Reimplementing any of that would introduce drift.

The operator/CI reviewed path has a narrower evidence contract: `render-source.mjs` always launches Chromium and waits for DOMContentLoaded. Both `automaticRenderedPayload` and `reviewedEnrichmentBatch` require `report.render` metadata; source-only evidence has no honest adapter today. `captureRows` already provides immutable hashing, resumability and authoritative fingerprint attachment, and `runRenderQueue` already preserves lease/apply pending receipts. Reuse those mechanisms.

Melanthi demonstrates why the missing adapter matters: fresh source HTML is substantial and available, but43 stylesheet/script requests queued through one-second guarded spacing exceed the30s navigation limit. The diagnostic did not reach DOM snapshot. This does not justify claiming a partial render or extending budgets.

## Proposed bounded patch

1. **Add an explicit capture mode in the existing source module.** Keep `renderOfficialSource` behavior available for compatibility; export an orchestrator such as `captureOfficialSource` from the same file. Fetch source once via `createSourceSession` and triage before choosing the mode. Reuse a private rendering helper accepting the already-fetched document/session so JS mode does not refetch or reset its budget.
2. **Source HTML mode is initially reviewed-only.** Require HTTP200, accepted same-host final URL, no aggregator/member-scope mismatch, no challenge and no JS-required shell. `html_available` alone is insufficient: it also classifies sparse pages; assess actual nonempty useful fields and identity evidence. Blank/generic HTML remains repair/checked-no-data and never replaces existing content. If substantive source omits dynamic content, preserve that coverage gap; do not claim the source mode completed it. Require explicit rendering for a known dynamic need rather than silently pretending source HTML contains it.
3. **Reuse the extractor unchanged.** Run the existing shared extractor on the fetched source. Do not add arbitrary supplementary crawling in this first slice. Existing worker supplementary behavior remains unchanged. Member/agency pages must retain their specific existing identity protections; source-only adapter should initially refuse unattended imports of these scopes, rather than borrow site-wide branding.
4. **Independently validate a small source-declared image set.** Select at most four unique candidate photographs from existing ranked/classified output (and a separately bounded logo only if needed), never guessed URLs. Fetch serially through the same robots/DNS-pinned/TLS/redirect-protected `sourceFetch`, same remaining overall40s/15MB budget, same request cap and host spacing, max8MB per image. Validate200, an allowed raster MIME plus matching magic bytes and a bounded decoder's actual dimensions; reject HTML responses, corrupt bytes, tracking pixels, excessive pixel counts and unsupported formats. Never trust width/height attributes as byte evidence. Store content-addressed bytes with URL/finalURL/hash/type/dimensions receipts and require human visual review for identity/subject/hero crop before applying. A URL loaded successfully is not proof that it depicts the business. Do not decode arbitrary SVG as trusted markup. If a decoder dependency is needed, pin it and review its bounds; this is an implementation prerequisite, not a dependency already present.
5. **Truthful evidence schema.** New schema-versioned captures have `capture_kind:'source_html'` with source SHA/title/finalURL, `render:null`, extractor hash and image receipts. Rendered captures retain their real render SHA. Never set render SHA equal to source SHA or call source-only evidence rendered. Original fetched HTML hash is retained separately from any sanitized retained HTML. Report source field availability, image verification and rendered journey as distinct states.
6. **Extend the existing reviewed adapter, not the writer/queue.** `reviewedEnrichmentBatch` accepts the discriminated source-only schema only after report hash, exact listing/source identity, reviewer/time, image review, current fingerprint and genuine lease all match. Persist an explicitly source-HTML evidence method and `official-source-html:` provenance; retain legacy rendered evidence compatibility. The adapter must merge reviewed machine additions with prior useful machine fields or fail closed on an unreviewed replacement—never clear a prior gallery just because no new photograph passed. Preserve owner fields/clears through existing `enrich_apply`, with current owner/source fingerprints checked again by that writer. No new tables, lease function or direct UPDATE.
7. **Do not broaden unattended promotion in the first release.** `automaticRenderedPayload` explicitly refuses/reports source-only captures as pending review, without pretending an error-only receipt is useful enrichment. Keep exact-title rendered identity guards intact. New source HTML routing should first be used in the existing operator capture/review flow. Enable queue routing only after the reviewed canary and preserved-pending-receipt behavior are accepted. Existing infrastructure preflight before credential/lease acquisition remains; no browser setup side effect should occur after leasing an unserviceable rendering task.

## Proposed ownership and tests before implementation

Candidate files: `scripts/enrichment/render-source.mjs` (capture routing/image evidence), `scripts/enrichment/render-capture.mjs` (mode-aware immutable capture), `scripts/enrichment/reviewed-batch.mjs` (schema-discriminated review), `scripts/enrichment/render-queue.mjs` (explicit source-only refusal/optional later routing), existing `tests/unit/rendered-source.test.mjs` plus an isolated image-byte verifier test if extracted. The shared Edge extractor, `_images.js`, source-fetch guards, current database migration/writer and production source rows need no change for this first slice. Agree ownership again before editing.

Required regressions:
- Substantive SSR uses zero browser launches and the unchanged extractor; a malformed/generic page cannot produce success from a title alone.
- JS shell retains protected browser rendering; challenge refuses before browser/image fetch; substantive contact CAPTCHA is not a full-page challenge.
- Source-only evidence cannot pass a rendered-only schema or unattended promotion gate. Legacy rendered reports still pass their original contract.
- Exact reviewer/hash/listing/source/fingerprint binding; stale source/owner/lease fail before apply. No fabricated lease and no retry of ambiguous apply.
- Image redirects check robots at every destination, private DNS is rejected, MIME/bytes mismatch and oversized/corrupt/pixel-bomb files rejected, cumulative deadline/byte budget enforced, no CSS/script storm on source-only path.
- A failed image cannot remove prior reviewed gallery or owner images. Logo, rating icons, decorative destination images and person/vendor identities do not auto-promote as venue photography.
- Fresh Melanthi canary only after tests and independent review: immutable source-only capture; inspect real photo bytes; independent identity/content review; parent obtains genuine matching lease, applies exact approved subset and checks base/owner hashes; verify actual canonical390/1440 gallery/contact and explicitly untested dynamic offerings.

## Operational boundary

No new successful Melanthi content capture exists yet. Prior protected timeout remains preserved. This proposal closes the evidence-adapter gap by reusing established extraction and write protections; it is not permission to relabel a normal-browser screenshot, skip image review or treat one hotel as site-wide completion.
