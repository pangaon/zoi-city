## Safely reusable now

The customer-owned `event_plan_save(p_plan,p_expected_version,p_request_id,p_data)` accepts a private draft `{title,kind:'other',timezone:'America/Toronto',private_notes:<bounded summary>,customer_name:<user-entered name>,customer_email:<user-entered email>,selections:[]}`. Name (1–120 characters) and email (at most160 characters, valid email syntax) are required by the existing backend even with no selections. The bridge collects them only when saving, never invents defaults, and retains them only in memory for an uncertain same-page retry; durable recovery metadata contains no contact details. Stable nonce and exact payload retry; existing `assets/event-planner/model.mjs` validates save receipts. `event_plan_get` and `event_plan_list` restore saved drafts. Store names/preferences/split intentions as private notes, not booking selections. The interface must say private plan, not secured table, paid split, received request or organizer confirmation. No business ownership assignment is required.

Existing venue editor and named-seat APIs provide versioned actual geometry, server seat IDs, atomic five-minute holds and free reservations only when a configured event/tier/owner/runtime exists. General-admission once/recovery APIs also require real future event inventory and currently support free tiers. Do not connect source table labels to these seat IDs or use the paid finalizer to manufacture a checkout. Paid finalizer is service-contained; provider credentials alone would not supply the missing inventory, quote, tax or settlement model.

Organizer setup still needs current authorized workspace ownership, an event record/date/timezone, reviewed real layout/table capacities, ticket types and currency/tax/bottle terms, capacity allocation and payment settlement/webhook/refund acceptance.
