BUILD MY LIVE ZOI DELIVERY DASHBOARD

Add a working, founder-only web dashboard to the existing Zoi operations area. Give George its live URL as soon as the first functional version is deployed.

This dashboard must track the entire existing delivery goal while implementation continues. Building it must not replace or suspend the main work.

PURPOSE

George should be able to open one page and immediately understand:
- What is actually working now.
- What changed since his last visit.
- How many profiles and addresses were genuinely corrected.
- Which specific records were affected.
- What is being worked on.
- What remains unfinished.
- What needs his action.
- Where to click to inspect or test a delivered result.

Use plain English. Keep technical evidence available under “Details.”

1. FIRST SCREEN

Show:
- Working now.
- Ready for you to try.
- Profiles improved and verified.
- Map locations corrected and verified.
- Remaining work.
- Needs your action.
- Last successful dashboard update.

Use real counts with clear definitions and denominators. If a value is unavailable, say “Not yet measured.” Do not substitute zero.

Do not invent a whole-platform completion percentage. Show progress separately for meaningful work areas. If scope changes, show that the total changed and why.

2. CLICKABLE PROFILE AND MAP PROGRESS

Provide separate counters for:
- Websites reviewed.
- Profiles enriched.
- Client homes visually checked.
- Client homes with working customer actions.
- Addresses actually corrected.
- Location-accuracy labels corrected.
- Records awaiting review or blocked.

Count unique records within each category. Updating five fields on one profile does not mean five profiles were fixed. Do not add overlapping categories together as a total.

Clicking a counter opens its actual records.

Each row should show:
Business/person name; category; location; what changed; verification status; completion time; and buttons to “Open profile,” “See changes” and “View evidence.”

Explain changes plainly, for example:
“Added the verified menu, corrected opening hours and connected the reservation link.”

Show before/after values where available. Do not manufacture historical values.

Keep coordinate correction separate from relabelling a city-centre location as approximate. Both are useful, but they are different outcomes.

3. A “READY FOR YOU TO TRY” FEED

When a customer workflow is deployed AND verified, create a card containing:
- What now works.
- Who it helps.
- What changed.
- A short suggested test.
- “Open it” or “Test it.”
- Web/mobile availability.
- Verification date.

The button must open the actual relevant profile or workflow, preserving necessary context.

Do not send George to a generic homepage and make him search.

For actions involving payment, messages or publication, provide a clearly identified test environment or safe walkthrough. Clicking “Test it” must not silently charge someone or contact real customers.

4. SHOW THE COMPLETE GOAL

Track the existing scope in understandable groups:
- Individual business and creator homes.
- Website research and enrichment.
- Maps and directions.
- AI and creative tools.
- Social publishing and email.
- Websites, SEO and analytics.
- Community, posts, reels and messaging.
- Shops, bookings and events.
- Owner workspaces.
- Mobile apps.
- Security and reliability.

Use these statuses:
Not started; being built; being tested; ready to release; live and verified; needs your action; blocked.

Every group should expand into concrete customer outcomes and remaining tasks.

A completed backend function does not automatically make the customer feature “Live and verified.”

5. REAL, AUTOMATIC UPDATES

Connect the dashboard to the existing authoritative work queue, enrichment/geocoding jobs, test results, CI, deployments and mobile release records.

Persist structured progress events. Update them from actual job and release lifecycle events wherever possible.

For work that requires an agent to record progress, show the timestamp and identify it as reported progress until independently verified.

Use live events or lightweight periodic refresh. Show when the data was last retrieved successfully.

Include an activity heartbeat. If updates stop, show “No recent update” and the last confirmed activity. Never leave an animated “Working” indicator running indefinitely without evidence.

Long-running jobs should expose actual processed, remaining, failed and retried counts.

Do not expose private model reasoning. Show observable work, outcomes and concise explanations.

6. REQUIRE PROOF BEFORE “LIVE”

Store the supporting record IDs, verification result and release identity for each delivered item.

Only mark a feature “Live and verified” when the required pieces are deployed and the actual customer journey passes.

Distinguish web deployment from native delivery.

For mobile, show the build/update identifier, included changes, testing status and installation link. A build made before a fix must not be shown as containing it.

If a release rolls back or a verification fails, update the dashboard. Do not leave stale green completion badges.

7. GIVE GEORGE AN ACTION INBOX

For each owner-dependent blocker show:
- What needs connecting or approving.
- Which features it blocks.
- The exact action required.
- A direct setup link where available.
- Whether there is a fee or provider review.
- How completion will be checked.

Do not display secrets.

Let George mark “I’ve done this,” then run the appropriate readiness check. His acknowledgement alone must not turn the integration green.

Provide a “Report a problem” action on delivered features. Save the report into the same delivery queue with the relevant profile, feature and release context.

8. MAKE IT CLEAR AND USABLE

Create a polished, responsive page with readable text, restrained colour and clear status labels.

Provide:
- “Since my last visit.”
- Search and filters.
- Recent activity.
- Clickable completed records.
- Failed/blocked items.
- Mobile release status.
- Expandable evidence.

Do not make George read logs, commit messages or test-suite names to understand progress.

Keep the dashboard founder-only with server-side authorization. Exclude unnecessary personal data and credentials.

9. VERIFY AND DELIVER IT

Demonstrate a real delivery item moving through the dashboard to deployed verification.

Confirm that:
- Counts reconcile with underlying records.
- Record links open the correct profiles.
- Live changes appear without a manual page reload.
- Stale updates are visibly identified.
- Failed verification prevents a green result.
- Reported problems persist.
- Unauthorized users cannot access it.
- It works on desktop and phone.

Reuse the existing operations infrastructure. Keep the first version focused and functional, then improve it while the full Zoi delivery continues.

Send George the working URL, how to access it, and which data feeds are connected. Clearly identify any feeds that are still being wired.

This page must become the reliable place George checks progress—not another manually maintained summary.
